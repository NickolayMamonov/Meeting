## Planning result

This revision supersedes the earlier planning comment where it conflicts, while preserving the valid module boundaries, FID-only authority, encrypted durable state, strict payload parsing, generic notification rendering, variant/release safeguards, and MEE2-51 joint beta gate.

### Resolved planning blockers

- **Published SDK freeze and compile gate:** pin Firebase BoM `34.16.0` and pin `firebase-messaging` explicitly to `25.1.1`. Google Maven currently publishes both artifacts, BoM `34.16.0` maps Messaging to `25.1.1`, and direct AAR inspection found public `FirebaseMessaging.register()`, `unregister()`, `FirebaseMessagingService.onRegistered(String)`, and `onUnregistered(String)`. The inspected AAR SHA-256 was `7b5f54a80179d72b14f5e0269a2bdd08c1d4e14beb4546ed227292e2e357c954`. Before implementation proceeds, Gradle dependency insight must resolve exactly `25.1.1` in this repository and a compile smoke test must call or override all four required symbols. If resolution or symbol compilation fails in local or CI environments, stop the implementation; `getToken`, `deleteToken`, `onNewToken`, and legacy `/profile/fcm-token` remain forbidden as fallback authority.
- **Navigation guarantee:** replace the unattainable exactly-once claim with durable **at-most-once navigation attempt plus idempotent same-route suppression**. Atomically claim a command before calling `NavController.navigate`. A crash after claim and before navigation can intentionally lose that navigation; claimed commands are never replayed after process death. Duplicate intents and an already-current matching meeting route produce no second navigation.
- **Permission UX:** explicitly authorize **no custom app-owned rationale, dialog, snackbar, or explanatory screen**. The contextual surface is the Android system `POST_NOTIFICATIONS` dialog itself, launched once from the resumed activity immediately after the first successful join signal. This is the only authorized UX change.
- **Install-scoped permission state and crash semantics:** permission policy is a separate install partition inside the aggregate and is never erased by logout, forced logout, profile deletion, account replacement, registration cleanup, or event cleanup. Only uninstall/app-data clear resets it. On API 33+, `REQUESTED` is committed before `ActivityResultLauncher.launch`; this intentionally provides an **at-most-once launch attempt**, not a guarantee that the dialog became visible. A crash or launcher failure after the commit and before dialog display is an accepted loss window and must not be recovered by re-prompting. Corrupt or unreadable state reconstructs permission as terminal `SUPPRESSED_CORRUPT`, never `NOT_ELIGIBLE` or `ELIGIBLE`, so corruption cannot re-enable prompting.
- **Representable event ownership:** model the ledger as a discriminated union rather than requiring owner fields on every record. `OwnedReminderEvent` contains the immutable owner snapshot and validated route fields. `DedupeTombstone` contains only event ID, terminal reason, terminal timestamp, and an optional owner snapshot: `DISCARDED_NO_OWNER` requires `owner = null`, while `DISCARDED_ACCOUNT_CHANGED` requires the prior owner. Tombstones contain no meeting ID or navigable payload and can never display, claim, or navigate.
- **No client-side 409 identity reset:** align Android with the bounded MEE2-51 ownership contract: POST/PUT resolve same-owner idempotency and cross-owner FID transfer atomically on the server. PUT 404 transitions to guarded POST; DELETE 404 is local idempotent success. Any POST/PUT 409 is an unexpected terminal `CONFLICT_BLOCKED` contract failure. Android does not call `FirebaseInstallations.delete()`, does not run an unregister/delete/register reset chain, and never falls back to token APIs.
- **Observable credential boundary:** extend the core-auth session boundary with non-secret `CredentialVersion(epoch, revision)`. `revision` is monotonic within an auth-store epoch and is updated atomically whenever a complete credential pair is successfully persisted, including login, relogin, account replacement, and same-session refresh. Normal auth clear preserves the epoch and revision even though it removes all credential/session keys. Expose `AuthCredentialState(session, credentialVersion)` as a distinct flow while preserving the existing `AuthSession` projection. A push 401 records the blocked version and can re-arm only after the same authenticated owner observes a newer version, after an authenticated epoch replacement caused by auth-store recovery, or after an owner/session-generation transition; `AuthSession(userId, stage)` alone is not a refresh trigger.
- **Bounded ledger contract:** cap the ledger at 512 records and retain display/dedupe history for at least 35 days. Only terminal or displayed records at least 35 days old are evictable; pending display records are never evicted. Pruning is deterministic. If the ledger remains full because every record is protected, new ingress fails closed without display or navigation. Exact event-ID dedupe is guaranteed while a record is retained and for at least the 35-day retention window; no dedupe guarantee is claimed after a record is validly evicted.
- **Bounded account exit:** explicit logout and post-deletion finalization have a frozen maximum of **4,750 ms**: a 4,000 ms non-cancellable orchestration budget followed by an unconditional, separately bounded 750 ms local auth-clear fallback in `finally`. Awaited work has individual timeouts; WorkManager cancellation, Firebase unregister, and notification cancellation are started but never joined. No Firebase, WorkManager, push-store, installation DELETE, server logout, or crypto operation can hold the UI exit path beyond the total bound.
- **Encrypted aggregate architecture:** the complete serialized `PushState` aggregate—not only the pending FID—is AEAD-encrypted. Registration owner/operation data, install permission policy, and the event ledger are ciphertext at rest. Typed DataStore writes `noBackupFilesDir/push/push_state.pb`; the Android-Keystore-wrapped Tink keyset is a binary file at `noBackupFilesDir/push/push_state_keyset.bin`. No push keyset is stored in SharedPreferences.
- **Non-authoritative unregistration callback:** `FirebaseMessagingService.onUnregistered()` carries no correlatable FID, owner, generation, or nonce, so it never mutates durable registration, installation, owner, operation, or ledger state. It is only a wake-up signal: while logged out it is ignored; while authenticated it schedules a fresh current-state reconciliation that may call `FirebaseMessaging.register()` but cannot clear or acknowledge anything. Logout/account cleanup advances generation and clears account-scoped state before starting the fire-and-forget Firebase unregister call. A delayed callback therefore either does nothing or requests an idempotent current-account registration, including after process death.
- **One reminder-only diagnostic contract:** normal reminders and the protected MEE2-51 diagnostic use the same data-only `MEETING_REMINDER` schema v1 and the same Android parser, ledger, renderer, and tap path. The backend supplies no FCM notification block that could bypass parsing. Android derives fixed generic copy from the validated offset and routes a valid tap to the validated meeting details; malformed or unknown payloads produce no display or navigation.
- **Executable installation response DTO:** POST accepts only `200` heartbeat or `201` create/transfer; PUT accepts only `200`. Their JSON body requires non-null `installationId`, `status`, and `lastSeenAt`, uses a canonical lowercase UUID, requires `status == ACTIVE`, and requires a strict UTC ISO-8601 `Instant` ending in `Z`. Additive unknown fields are ignored without being persisted or logged, but a returned `fid` field is explicitly forbidden. PUT additionally requires the response installation ID to equal the requested path ID. Every other 2xx/status/body combination is a terminal malformed-contract result.
- **Complete old-owner tombstoning:** account cleanup converts every `OwnedReminderEvent` for the departing owner/generation—including `PENDING_DISPLAY`, `DISPLAYED`, `NAVIGATION_CLAIMED`, and `NAVIGATED`—to an owner-bearing `DISCARDED_ACCOUNT_CHANGED` tombstone in the same atomic mutation. It retains only event ID, former owner snapshot, and terminal time; no old-owner route survives cleanup.

### Ordered implementation plan

1. **Preserve and reconcile worktree state.** Snapshot HEAD, status, and diff and retain all existing session changes. During coding, replace the partial legacy token and Firebase Installations polling implementation with this plan without touching unrelated work. Do not reset authenticated emulator or device state. Confirm the release origin remains exactly `https://api.whysoezzy.online` and preserve debug and snapshot behavior.

2. **Freeze dependencies and block on FID API availability.** In the catalog and build, use BoM `34.16.0`, exact Messaging `25.1.1`, WorkManager runtime, typed DataStore, Tink, and the Koin WorkManager integration. Do not add a Firebase Installations dependency: Android neither reads nor deletes the Firebase Installation. Add a source compile fixture proving `register`, `unregister`, `onRegistered`, and `onUnregistered`; add dependency-insight verification for selected `25.1.1`. `FirebaseInstallations.id` must never be read or polled.

3. **Keep the backend contract additive and typed.** Add a separate profile-domain `PushInstallationRepository` and profile-data API, DTO, and repository for authenticated `POST /profile/push-installations {fid}`, `PUT /profile/push-installations/{installationId} {fid}`, and `DELETE` only. FID is a nonblank opaque UTF-8 write-only value bounded to the MEE2-51 maximum; Android does not infer Firebase syntax and never echoes it. Freeze successful response decoding with explicit non-null required fields and additive compatibility (`ignoreUnknownKeys = true`): `installationId`, `status`, and `lastSeenAt` must each be present exactly once, while unknown fields are ignored and never persisted or logged. Before typed decode, reject any top-level `fid` field so the response cannot silently violate the write-only credential contract. `installationId` is exactly 36 ASCII characters and must round-trip unchanged through `UUID.fromString(...).toString()`, thereby requiring canonical lowercase hyphenated form; after validation it remains an opaque string. `status` accepts only the exact wire value `ACTIVE`. `lastSeenAt` must match `YYYY-MM-DDTHH:MM:SS[.1-9 fractional digits]Z`, contain no surrounding whitespace, and parse with `java.time.Instant.parse`; offsets such as `+00:00`, local timestamps, lowercase `z`, and more than nine fractional digits are invalid. POST accepts only `200` for a same-owner heartbeat and `201` for a new/cross-owner destination row; PUT accepts only `200` and the response `installationId` must equal the canonical path UUID. A different 2xx, empty body, duplicate/missing/null required field, forbidden `fid`, malformed identifier/timestamp, non-`ACTIVE` status, or PUT ID mismatch is a terminal `MALFORMED_SUCCESS` that cannot acknowledge or discard the guarded FID. DELETE accepts only empty-body `204` success or the frozen static `404` idempotent completion. Keep `/profile/fcm-token` isolated as legacy compatibility with no binding into the new state machine. Ktor and repository tests assert exact paths and bodies, auth metadata, all valid status-code branches, ignored additive-field behavior, and malformed/semantic-invalid fixtures.

4. **Use one fully encrypted, typed durable aggregate with an install/account partition.**
   - Define a versioned Kotlin serialization model `PushStateV1` and encode/decode it with `kotlinx.serialization` ProtoBuf. It contains `InstallPolicyState`, `RegistrationState`, and a bounded `PushEventLedger`. `InstallPolicyState` owns notification-permission values and is not account-scoped. `RegistrationState` contains immutable `ownerUserId`, monotonic `accountGeneration`, operation `nonce`, installation ID, pending FID, operation kind, retry/401 metadata, and terminal contract status. It contains no Firebase identity-reset phase or reset marker.
   - Make ledger records a serialized discriminated union. `OwnedReminderEvent(eventId, ownerUserId, ownerGeneration, meetingId, reminderOffsetMinutes, issuedAt, receivedAt, status, statusChangedAt)` is the only variant that can be displayed or tapped. `DedupeTombstone(eventId, reason, terminalAt, owner?)` has no meeting/route fields: `DISCARDED_NO_OWNER` requires `owner == null`; `DISCARDED_ACCOUNT_CHANGED` requires the former `ownerUserId` and `ownerGeneration`. Decode validates these invariants and treats an unknown variant, impossible owner/reason combination, or route fields on a tombstone as aggregate corruption. Migration converts existing owner-bearing terminal discards to the appropriate tombstone and never fabricates an owner for `DISCARDED_NO_OWNER`.
   - Freeze ledger bounds at 512 records and a 35-day minimum retention measured from `statusChangedAt`/`terminalAt` using an injected wall clock. Before insertion, remove only records that are both evictable and at least 35 days old: `DISPLAYED`, `NAVIGATION_CLAIMED`, `NAVIGATED`, and both tombstone reasons are evictable; `PENDING_DISPLAY` is not. Evict oldest eligible timestamp first, then lexicographically smallest event ID as a stable tie-break. The atomic prune returns IDs for any evicted `DISPLAYED` notifications so the coordinator can best-effort cancel them; a tap racing cancellation finds no ledger route and safely performs no meeting navigation. Never evict a protected record merely to admit a new one. If capacity remains 512, reject the new event with a typed `LEDGER_CAPACITY_BLOCKED` result and perform no notification/navigation side effect. Redelivery remains suppressed for every retained event ID and for at least 35 days; after deterministic age-based eviction, a later redelivery may be treated as new and that limitation is explicit.
   - Encrypt the entire serialized `PushStateV1` byte array with one dedicated Tink AEAD primitive before DataStore writes it. The DataStore serializer persists only a small envelope containing format version plus ciphertext; associated data binds the ciphertext to the push-state file and schema family. Therefore FID, installation ID, owner ID, permission state, operation metadata, and event records are all encrypted at rest.
   - Create DataStore explicitly with `DataStoreFactory.create(serializer = ..., produceFile = { File(context.noBackupFilesDir, "push/push_state.pb") })`. Store the Tink keyset at `File(context.noBackupFilesDir, "push/push_state_keyset.bin")`, encrypted with an Android Keystore master key and file-specific associated data. Create the parent directory privately. Do not use `preferencesDataStore`, `Context.dataStoreFile`, `AndroidKeysetManager.withSharedPref`, or a backup-enabled path for push state/key material. Backup XML may retain defense-in-depth exclusions for the old unshipped store but is not the mechanism that makes the new files no-backup.
   - On first secure-store initialization, perform a one-way migration that deletes the unshipped plaintext `pending_push_registration_store.preferences_pb` without reading or replaying its FID and records the migration version inside the encrypted aggregate. Future typed migrations operate on decrypted versioned models and rewrite atomically. Unknown future schema versions, malformed envelopes, AEAD failure, missing/corrupt keyset while state exists, and serialization failure all enter the same fail-closed recovery.
   - Distinguish pristine install from corruption: absence of both state and keyset creates `InstallPolicyState.NOT_ELIGIBLE`; any unreadable/inconsistent existing artifact is quarantined/replaced with a fresh encrypted state whose permission value is terminal `SUPPRESSED_CORRUPT`, whose registration requests a fresh Messaging registration callback without reading an FID, and whose ledger is empty. Account cleanup uses one atomic `clearAccountScopedState` mutation that advances generation, clears the old registration owner/installation/operation fields, and replaces **all** `OwnedReminderEvent` records for the departing owner and generation—regardless of `PENDING_DISPLAY`, `DISPLAYED`, `NAVIGATION_CLAIMED`, or `NAVIGATED` status—with `DedupeTombstone(reason=DISCARDED_ACCOUNT_CHANGED, owner=oldOwner)`. Each replacement retains only event ID, former owner ID/generation, and cleanup time; it removes meeting ID, offset, issued/received timestamps, display/navigation status, and every route-bearing field. Existing tombstones remain terminal, the install permission partition/state file/keyset are preserved, and the mutation returns all old-owner notification IDs for best-effort cancellation.

5. **Implement the FID registration reducer, callbacks, and credential version.** Manifest enables `firebase_messaging_installation_id_enabled=true`; ingress-only `MeetFirebaseMessagingService` stages `onRegistered(fid)` and receives `onUnregistered()` without navigation or identifier logging. Because `onUnregistered()` has no FID, owner, generation, or nonce, it is permanently **non-authoritative**: it cannot clear/change/acknowledge pending FID, installation ID, owner, account generation, operation, nonce, retry state, or event records, and there is no persisted “matching unregister expectation.” Its only allowed effect is a process-local wake-up to reconcile from the current durable state. If the current session is logged out, reconciliation is a no-op. If authenticated, reconciliation requests `FirebaseMessaging.register()` and accepts any resulting `onRegistered(fid)` as fresh installation-wide evidence to be bound through the current owner/generation reducer; an already-bound identical FID reduces to an idempotent no-op/heartbeat. Logout, deletion, and account replacement first atomically advance generation and clear/tombstone account-scoped state, then start `unregister()` without awaiting it. Thus a callback delivered out of order, duplicated, after a newer `onRegistered`, after an A-to-B switch, or after process recreation can only cause a current-state register/reconcile and can never erase newer state. The coordinator observes durable `AuthCredentialState(AuthSession(userId, stage), CredentialVersion(epoch, revision))` and increments push account generation for every owner transition, including same-process logout and login.
   - In core auth, persist non-secret `credential_epoch` and `credential_revision` in `secure_token_store`. Every mutation that currently calls `Preferences.clear()` must preserve these two metadata keys. TokenManager `saveAuthenticated` and every `saveTokens` write whose post-write state contains a complete access-token/refresh-token/user-ID tuple increment the revision in the same DataStore edit that writes that tuple and stage; an orphan pair with no resolvable user ID is incomplete and does not increment. Stage-only writes and failed/incomplete credential writes do not increment it. `clearTokens`, explicit logout, forced clear, repair of invalid auth keys, and account deletion atomically remove all credential/session keys but preserve and emit the current credential version with `AuthSession.LoggedOut`.
   - Scope one epoch to the lifetime of a readable auth preference store. Migration of a valid legacy authenticated store with no version creates a random 128-bit epoch and revision `1`; a legacy logged-out/pristine store starts at revision `0`. Same-user relogin, different-user login, and account replacement continue incrementing the preserved revision. Process recreation reads the same version. If the auth store is corrupt/unreadable, fail logged out, create a new random epoch with revision `0`, and require the next complete authenticated write to produce revision `1`; an authenticated epoch change is treated as a new credential boundary rather than comparing numeric revisions across epochs. On `Long.MAX_VALUE`, rotate the epoch and write revision `1` atomically with the new credentials. Expose the credential-state flow through `AuthSessionRepository` (or a sibling core-auth repository backed by the same `TokenManager`), while existing `session` remains a mapped/distinct compatibility projection. No token value, hash, or timestamp is exposed.
   - A logged-out FID may be part of the encrypted unbound registration state, but it cannot create an event owner or network request. Authenticated no-installation uses CREATE; changed FID with a valid installation uses ROTATE. Every async result commits only when owner, generation, operation, and nonce still match.

6. **Freeze HTTP recovery semantics.** The worker branches on `ApiException` metadata status even though `safeApiCall` maps both 401 and 403 to `UnauthorizedError`.
   - POST `200` heartbeat, POST `201` create/transfer, and PUT `200` acknowledge only after the strict response DTO validation in step 3; PUT also requires returned/path installation-ID equality. No other 2xx is valid. DELETE empty-body `204` succeeds; DELETE static `404` is idempotent local success.
   - PUT 404 means the installation expired or disappeared: clear only the stale installation ID, preserve the guarded pending FID, and transition to POST CREATE.
   - MEE2-51 must freeze an atomic ownership matrix before beta promotion: POST with a new FID creates an active installation; POST with the same owner/FID heartbeats idempotently; POST with a FID owned by another account atomically transfers or rebinds it without 409; PUT requires current ownership of the opaque installation, preserves that installation ID, and atomically clears/deactivates any conflicting prior FID owner before assigning the submitted FID. Responses remain sanitized and never return FID.
   - PUT 404/non-enumerating not-owned means the local installation binding is stale: clear only the guarded installation ID, preserve the current pending FID and owner/generation/nonce, then transition to POST CREATE. DELETE 204 and DELETE 404 both complete local cleanup. Any POST/PUT 409 is outside the frozen contract: atomically enter terminal `CONFLICT_BLOCKED`, preserve only sanitized status metadata, return WorkManager success, and require a newer FID callback, owner generation, or app update/operator diagnosis before another network attempt.
   - A 409 must not call `FirebaseMessaging.unregister()`, `FirebaseMessaging.register()`, or `FirebaseInstallations.delete()`; must not clear the current FID merely to manufacture a different identity; and must not fall back to `getToken`, `deleteToken`, `onNewToken`, or `/profile/fcm-token`. This removes the unbounded Firebase Task/callback chain entirely. Tests assert that unexpected 409 remains terminal across process death and account-stable app restart, stale worker completions cannot clear it, and no Firebase identity API is invoked.
   - 401 preserves pending work as `BLOCKED_AUTH` together with `blockedCredentialVersion`, returns success to stop the current WorkManager burst, and does not force logout. For the same authenticated owner/epoch it re-arms only when `revision > blockedRevision`; an authenticated epoch change after auth-store recovery also re-arms as a new credential boundary, as does a different valid owner/session generation. Logged-out emissions, app foreground, cooldown expiry, process restart, and an unchanged `AuthSession(userId, stage)`/credential version do not re-arm a 401.
   - 403 is terminal `FORBIDDEN` for that owner generation, with no automatic network retry and no auth mutation.
   - Network errors, 408, 429, and 5xx retry; POST 404, other permanent 4xx, malformed 2xx bodies, and any unexpected 409 are terminal contract states. Tests assert preserved status metadata.
   - Cap each transient WorkManager burst at six attempts with exponential backoff. At the ceiling, atomically record `SUSPENDED_RETRY_EXHAUSTED` and return success so WorkManager does not hot-loop. Recovery from transient exhaustion is explicit: app start or foreground after a persisted cooldown, a newer credential version under the rules above, an owner/session change, or a new Firebase registration callback re-arms one fresh six-attempt burst. The stricter `BLOCKED_AUTH` rule above still applies to 401. No self-rescheduling loop runs forever in the background.

7. **Freeze WorkManager construction and replacement.** Use the official Koin AndroidX WorkManager `WorkerFactory`, installed from `MeetApplication` configuration, and remove or disable the default WorkManager initializer so there is one factory and initialization path. `PushReconcileWorker` receives dependencies through that factory and reads current durable state rather than trusting WorkRequest input. Enqueue fixed unique work name `push-registration-reconcile` with network constraint and `ExistingWorkPolicy.REPLACE` for every material state, session, or FID transition. Logout, deletion cleanup, and account replacement cancel that unique work first; replacement plus generation and nonce CAS prevents an old-account retry from delaying or acknowledging new-account work.

8. **Freeze explicit exit composition, awaited/fire-and-forget work, and hard budgets.** Define a profile-domain `AccountExitCoordinator` interface with `logout()` and `deleteAccount()`; provide the concrete app-level implementation in app glue and push DI because `:app` can compose profile domain, core auth, and push without reversing dependencies. `ProfileDetailsViewModel` and `ProfileEditViewModel` depend on this coordinator instead of directly composing `LogoutUseCase` and deletion plus logout.
   - Refactor the existing core-auth logout implementation so its remote logout call is bounded and its local clear remains unconditional; it must not contain an unbounded `NonCancellable` operation. The app coordinator also owns a direct `AuthSessionRepository.clear()` fallback so auth clearing is attempted even if orchestration fails before or during `LogoutUseCase`.
   - For explicit logout, enter `withContext(NonCancellable) { withTimeoutOrNull(4_000) { ... } }` before reading push state. **Awaited and individually bounded:** one atomic state snapshot/generation-advance/account-cleanup transaction that also returns the installation DELETE input (500 ms), authenticated installation DELETE while credentials exist (1,250 ms), and bounded `LogoutUseCase` remote phase (1,250 ms). **Started but never awaited/joined:** `WorkManager.cancelUniqueWork("push-registration-reconcile")`, `FirebaseMessaging.unregister()`, and cancellation of old-owner notifications. Their returned `Operation`/`Task` handles are intentionally ignored after start; generation/nonce invalidation makes late completion harmless.
   - In the outer `finally`, always invoke local `AuthSessionRepository.clear()` under a separate 750 ms `NonCancellable` timeout, even if the 4,000 ms block timed out, threw, or was cancelled. Return control/navigation after that attempt. The maximum post-command exit delay is therefore 4,750 ms. A failed/timed-out push-store mutation must never delete the install permission partition; subsequent auth observation performs idempotent stale-owner cleanup.
   - Account deletion first invokes `DeleteCurrentUserProfileUseCase` in caller context with existing UX/cancellation behavior. On failure, retain auth and push binding exactly as today. On success, run the same 4,000 ms finalization plus 750 ms auth-clear fallback, but do not call installation DELETE: MEE2-51 must confirm profile deletion cascades installations because the profile/resource may already be gone. The finalization awaits only the 500 ms account-state mutation and bounded core-auth logout; WorkManager cancellation, unregister, and notification cancellation remain fire-and-forget.
   - Forced logout is observed after auth has already become logged out. It starts WorkManager cancellation, Messaging unregister, and notification cancellation without joining them, and attempts account-scoped store cleanup for at most 500 ms. It never calls server logout or installation DELETE and cannot delay auth navigation. Tests use virtual time/fakes to prove every individual bound and the 4,750 ms total, including non-completing WorkManager `Operation`, Firebase `Task`, store mutation, installation DELETE, server logout, and caller cancellation.

9. **Bind owned events to one account generation and freeze the sole reminder/diagnostic wire contract.** `MeetingReminderParser` accepts a data-only message whose key set is exactly `{eventType, schemaVersion, eventId, meetingId, reminderOffsetMinutes, issuedAt, destination}`; unknown or missing keys, a Firebase notification block, null-equivalent/blank values, or surrounding whitespace fail closed. Values are exact: `eventType=MEETING_REMINDER`, `schemaVersion=1`, `destination=MEETING_DETAILS`; `eventId` is a canonical lowercase hyphenated UUID that round-trips through `UUID`; `meetingId` is a canonical positive base-10 `Long` with no sign or leading zero; `reminderOffsetMinutes` is exactly `60` or `1440`; and `issuedAt` follows the same canonical UTC `Instant` rule as step 3. Normal reminders and MEE2-51 `POST /admin/push/diagnostic` `SINGLE|DEDUP_PAIR` use this identical schema; the diagnostic accepts exact user/installation/joined-meeting/offset/mode targeting, generates event ID/time server-side, and `DEDUP_PAIR` sends two byte-identical data maps. The backend sends no FCM notification presentation block. Android derives `Meeting reminder` plus `A meeting you joined starts in 1 hour.` or `A meeting you joined starts in 24 hours.` only after validation.
   - At receipt with an active authenticated registration owner, insert `OwnedReminderEvent` with immutable `ownerUserId` and `ownerGeneration` before display. Receipt while logged out, without a bound owner, or during owner mismatch inserts `DedupeTombstone(reason=DISCARDED_NO_OWNER, owner=null)` using only the validated event ID and terminal timestamp; it stores no meeting ID/route and is neither displayed nor navigated.
   - On logout, forced logout, successful deletion finalization, or account change, atomically replace **every** old-owner `OwnedReminderEvent`, including already claimed or navigated records, with `DedupeTombstone(reason=DISCARDED_ACCOUNT_CHANGED, owner=oldOwner)` and best-effort cancel any associated notification. No claimed/navigated route record is retained. Tombstones remain terminal and tap-ineligible regardless of current account, while their retained event IDs continue dedupe within the normal retention window. A tap is consumable only for an `OwnedReminderEvent` whose owner exactly matches the current durable auth user and generation. Tests cover each source status, all-record atomic conversion, serialization/restart, no residual meeting/route fields, receive under A then logout/login B, delayed old intent, process death before/after account change, logged-out receipt, and stale notification cancellation.

10. **Keep display idempotent and privacy-safe.** Persist validated event data before rendering. Use one versioned stable channel, generic no-PII resources, and `notify(tag=eventId, id=constant)` so a retry replaces the same notification rather than creating a duplicate. Mark displayed after `notify`; a crash in that gap may repeat `notify`, but the user-visible result remains one notification. Pending display drains on receipt, app start, and permission or settings grant. Unknown or malformed payloads fail closed. Never log FID, payload values or full payloads, auth material, meeting or user or location content, or notification body.

11. **Implement attainable navigation semantics.** Internal explicit intents carry validated event ID and meeting ID and must equal the durable ledger record. `MainActivity.onCreate` and `onNewIntent` feed a typed inbox. A Compose effect beside `MeetNavHost` waits for graph readiness and an exact owner match, then atomically transitions `DISPLAYED -> NAVIGATION_CLAIMED` before any `NavController` side effect. If claim fails, do nothing. If the matching meeting route is already current, suppress navigation and mark complete; otherwise navigate through existing `MeetRoute.MeetingDetails` with `launchSingleTop`, then best-effort mark `NAVIGATED`. `NAVIGATION_CLAIMED` is terminal for replay: process death in the claim-before-navigate window may lose the navigation by design, but it cannot duplicate it. Logged-out or account-changed taps open only the existing default or auth flow and durably discard the command.

12. **Implement the authorized install-scoped permission policy.** A generic meeting-joined signal is emitted only after `JoinMeetingUseCase` succeeds. App routing atomically changes install permission from `NOT_ELIGIBLE` to `ELIGIBLE`; on API 33+ the next resumed activity commits terminal `REQUESTED` before invoking the system permission launcher. There is no custom rationale surface or copy.
   - `REQUESTED` survives every account cleanup and is never reset by denial, dismissal, logout, forced logout, deletion, A-to-B replacement, registration reset, app restart, or app upgrade. Only uninstall/app-data clear creates a new pristine install.
   - If the process crashes, the activity stops, or launcher invocation throws after `REQUESTED` commits but before the OS dialog appears, do not retry. This accepted crash-loss window is the cost of the no-repeat guarantee and must be an explicit unit/instrumentation case.
   - Corrupt-state recovery uses `SUPPRESSED_CORRUPT`, which is also terminal and cannot transition to `ELIGIBLE` or launch a request. A later settings grant is detected from OS state and drains pending display without changing the no-prompt terminal state. Pre-33 is treated as granted. Preserve current join rollback, profile toggle, and all unrelated UI.
